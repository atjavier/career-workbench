# Adversarial Review — Profile-led Resume Architecture

**Verdict:** Changes required before Epic 8 stories are created. The spine sets the correct boundaries, but several literal, independently valid implementations would not interoperate safely.

## Findings

1. **High — claim provenance cannot be constructed deterministically.** The gateway response accepts `claims[]` but has no per-claim selected-evidence reference. Meanwhile `material_claim_support` is mandatory and review blocks claims without it. One compliant gateway can return only text; one compliant repository can require joins; the result is either every draft permanently blocked or a dangerous implementation that attaches every selected evidence revision to every claim. Bind a response field such as `supportingEvidenceDigests[]` per claim, require it to be a non-empty subset of the selected evidence, mint application claim IDs, and insert all claims/support rows in the same transaction as the draft.

2. **High — template pinning is asserted but not represented as a required snapshot.** `material_drafts` and `material_versions` require a template-source FK and generic provenance digest, while AD-13/AD-8 require the template SHA-256 to be pinned on each record. A repository can literally store only the FK, and a file/metadata repair can then make historic material unverifiable. Require a non-null `template_digest` column on both records, enforce equality with the referenced source on insert, and make the preview/render commands rehash the stored byte copy against that snapshot.

3. **Medium — consent does not cover the user request itself.** `consentFingerprint` omits `userRequest`, and the UI is only required to show selected material names. A client can obtain consent, alter the prompt, and submit with the same valid fingerprint. Bind the fingerprint to a normalized user-request digest and require the consent panel to disclose that exact request (or invalidate consent whenever it changes).

4. **Medium — file/SQLite bootstrap lacks an atomic-recovery contract.** The template bootstrap promises a file copy plus a database transaction, but the two resources cannot commit atomically. A valid implementation can leave a final private PDF orphaned when DB insertion fails, or designate a source whose final byte copy was never atomically published after a crash. Specify a staging manifest/state, atomic rename before/after the DB action, startup cleanup/reconciliation rules, and the exact rule that a designation is valid only when its final path rehashes to the stored digest.

5. **Medium — LocalModelGateway token ownership remains ambiguous.** The gateway requires an LM Studio token but its contract does not bind how it is obtained. One implementation can read it from a browser request or environment variable; another can use the OS vault, both otherwise meeting the written request-body/log rules. Require server-side retrieval from the OS credential vault by a fixed credential key, no browser/API response exposure, and a safe unavailable-token error before any request.

6. **Low — the singleton and immutable constraints need database-level forms.** The seed names `resume_generation_state` a singleton and tables immutable, but does not bind a fixed singleton key/uniqueness rule or trigger coverage for join rows and state updates. Require the migration to enforce exactly one state row, approved-evidence-only inserts, and `UPDATE`/`DELETE` rejection for every revision, draft, claim, support, template, and version table; retain updates only on the state pointer.
