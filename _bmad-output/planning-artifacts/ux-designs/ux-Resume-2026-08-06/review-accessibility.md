# Accessibility & Responsive-Behavior Review

**Verdict: needs revision before implementation.** This review assesses the final UX spines as a behavioral contract, not an implementation. The baseline is materially better than the prior privacy/accessibility review: it already requires keyboard operation, contained modal focus, 24px targets, status announcements, and non-hover-only controls. The findings below are the remaining gaps that can still produce inaccessible or unreliably responsive implementation.

| Severity | Location | Finding | Required UX fix |
|---|---|---|---|
| High | DESIGN.md: colors 15–16; Components / `button-primary` | The declared primary pair is not AA compliant. `#F59E4A` with white text is approximately **2.1:1**, despite the spine requiring 4.5:1. It is assigned to Refresh, Generate draft, Export, and Retry—the actions the product relies on users being able to identify. This is a token-level contradiction, not an implementation choice. | Replace the primary foreground/background pair with a measured 4.5:1-or-better pair for normal text (and keep it compliant in hover, pressed, disabled, and focus-visible states). Record the measured contrast in the token definition; do not let component teams choose a substitute ad hoc. |
| High | EXPERIENCE.md: Responsive & Platform 153–155 | Phone support is conditional precisely where the product’s consequential work occurs: “large document editing/export remains available only if it can preserve” review access. This supplies no behavior if it cannot. A phone user can reach a blocked workflow with neither a usable editor/export flow nor a stated safe deferral path. | Specify a deterministic phone policy for Draft and export: either define the fully accessible mobile flow, or intentionally defer those actions with an always-available, accessible explanation, preserved local state, and a non-destructive resume-on-larger-screen path. Test the selected policy for warnings, provenance, acknowledgement, and export failure. |
| Medium | DESIGN.md: Layout & Spacing 86; EXPERIENCE.md: Interaction Primitives 135; Responsive & Platform 151–155 | “Tables or stacked records according to available width” is not a responsive contract. There is no field-to-card mapping, header association rule, action placement, sort/filter continuity, or breakpoint/reflow acceptance criterion. Implementations can technically retain fields while making card records ambiguous or forcing horizontal scrolling. | Define the Jobs and Tracker narrow-record schema: visible label/value pairs for every required field, repeated contextual title/company on actions, an accessible record name, and preserved sort/filter/result-count state. Set acceptance at 320 CSS px and 400% zoom/1280 CSS-px viewport: no loss of content/functionality and no two-dimensional scrolling except an explicitly justified data region. |
| Medium | DESIGN.md: CV Builder Reference Update 74; Components / Resume editor and preview 107; EXPERIENCE.md: Component Patterns 94 | Narrow layouts always place the editor before preview, but the editor can be long. The preview, claim warnings, and evidence comparison can therefore sit after a large editable form, turning a review-before-export workflow into a scroll endurance test. “Logical reading order” does not resolve this conflict. | Define the narrow-screen review sequence and navigation: keep an in-flow, programmatically named review summary/warning count before editing; provide labelled jumps between editor, preview, warnings, and provenance; return focus to the invoking section. Do not make a sticky preview or floating control obscure focused content. |
| Medium | EXPERIENCE.md: Application shell 19; DESIGN.md: Layout & Spacing 86 | The small-screen “compact navigation control” has no interaction contract. Seven primary destinations are being compressed without requirements for current-page exposure, keyboard/screen-reader behavior, focus movement, Escape/outside-close behavior, or preserving the user’s current scroll/form state. | Specify the compact navigation as a native button plus labelled navigation region: expose the current destination, support keyboard and touch operation, close predictably (including Escape), restore focus to the trigger, and preserve unsaved-edit protection. State whether it is a disclosure, dialog, or other pattern so semantics are consistent. |
| Medium | EXPERIENCE.md: Accessibility Floor 140–147; State Patterns / Cold load 113 | “WCAG 2.2 AA intent” is too soft for implementation and testing. The document names reflow and focus generally but provides no response to text spacing overrides, orientation changes, or loading skeletons that can trap focus, be announced repeatedly, or masquerade as data. | Turn the floor into testable acceptance criteria: keyboard-only, screen-reader, 200% text spacing, 400% zoom/reflow, portrait and landscape, and reduced-motion/no-motion journeys. Require loading placeholders to be non-focusable, unavailable to assistive tech unless meaningful, and replaced by one concise status update rather than repeated announcements. |
| Low | DESIGN.md: Typography 82; EXPERIENCE.md: Responsive & Platform 154–155 | The only typographic rule for long source text is wrapping. It does not define how quoted posting language, provenance URLs, filenames, timestamps, and rich-editor content behave under zoom or narrow widths. These are exactly the unbroken strings that commonly cause clipping or horizontal scrolling in job and evidence records. | Add overflow rules: wrap or safely break long URLs/filenames, preserve selectable source text, avoid truncating material facts, and provide an accessible full-value disclosure where visual truncation is unavoidable. Verify these rules in stacked records and the draft editor. |

## Exit criteria

Resolve both High findings before visual implementation. Then validate UJ-1 through UJ-4 with keyboard only and a screen reader at the defined narrow/reflow conditions, including a long job title/URL, a long Draft with a blocking warning near its end, a compact-navigation transition with unsaved edits, and a Tracker record with all required fields and actions.
