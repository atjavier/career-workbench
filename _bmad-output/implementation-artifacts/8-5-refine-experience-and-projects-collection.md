# Story 8.5: Document source folders and review Experience & Projects artifacts

Status: done

## Story

As Adrian,
I want to document real local Project and Experience working folders into reviewable resume artifacts,
so that source code and other working material never become resume evidence or claims without explicit, traceable review.

## Acceptance Criteria

1. **Resume-consistent collection.** Given Adrian opens **Resume > Experience & Projects**, when the page renders at any viewport, then it uses the same page header, outer Resume mini-tabs, typography, spacing, selected underline, visible focus treatment, and 320 CSS-px single-column reflow as **Resume > Edit**. It provides an inner keyboard-operable **Projects** / **Experiences** tablist (`role="tablist"`, `role="tab"`, `aria-selected`, labelled panel) and shows only the selected category's compact collection.

2. **Native local-LLM documentation.** Given Adrian documents an item, when he chooses the single **Document project folder** or **Document experience folder** action for the selected category and explicitly consents, then the application sends only a bounded, allowlisted snapshot of that real working folder to the registered local-LLM documentation skill. The flow states the source is read only, produces exactly `project-overview.md`, `resume-evidence.md`, and `resume-bullet-candidates.md`, and does not auto-approve evidence. The active page offers no Codex prompt, typed Markdown entry, one-file picker, direct raw-source import, Base Resume extraction, or `Resume.pdf` import/extraction control.

3. **Strict agent and skill boundary.** Given the application-native agent runs its registered resume documentation skill, when it receives the selected source snapshot, then the registry enforces typed inputs/outputs, declared readable roots/extensions/exclusions, depth/file/byte limits, writable destinations, consent, and prohibited operations. The agent cannot invoke Codex, shells, arbitrary tools, network/cloud/model services beyond the configured local LLM, credentials, database handles, watchers, background work, retries, recursive unregistered skills, or source mutation. It excludes dependency, VCS, build, coverage, cache, generated, binary, opaque, and unsupported content; snapshots source state; and publishes exactly three proposed artifacts only after validation. Every retained fact is atomic, marked proposed/unreviewed, has slash-formatted source-relative path plus nearest heading (or `document`) and one-based line provenance, and preserves explicit unknowns for unsupported ownership, metrics, users, dates, outcomes, deployment status, and skills.

4. **Generated artifacts and review integrity.** Given the local skill returns its exact three artifacts, when the application validates and stores them for the selected category, then it creates proposed/unreviewed evidence only from valid `resume-evidence.md` E-items with artifact-backed source-relative provenance and preserves individual approval/revision/audit behavior. `project-overview.md` and bullet candidates remain review artifacts, not claim-eligible evidence. A failed, malformed, unsafe, oversized, stale, or concurrent run leaves application state and the source folder unchanged; no raw source bytes or private model diagnostics are persisted or displayed.

5. **Safe compact rows and details.** Given a category has imported documentation, when Adrian scans or expands a row, then it shows a friendly import name, one local summary, `3 proposed review documents`, evidence-item count, and a plain-language review state. A native **View details** control has `aria-expanded` and `aria-controls`; its details show only the three generated artifact names and individually scoped existing review controls. Neither row nor details exposes raw source paths, internal IDs, digests, prompts, model data, parser diagnostics, Base Resume records, or `Resume.pdf`. New evidence remains **Ready for review** and cannot be supplied to Resume Coach until individually approved.

6. **Summary, recovery, and legacy boundaries.** Given `project-overview.md` is displayed in a row, when its summary is derived, then it deterministically removes front matter, HTML comments, headings, blank lines, and fenced code; normalizes a leading list marker; takes the first meaningful paragraph; limits it to one sentence and 240 characters; otherwise displays **No summary found yet.** The summary is never evidence, claim eligible, or AI-generated by the app. Given a keyboard, screen-reader, narrow-screen, or failure path, then label associations, visible focus, `aria-live="polite"` atomic status, duplicate-submit prevention, predictable focus, and a concise safe recovery action are preserved. Legacy Base Resume data remains preserved but unread and unmodified by this flow, and `Resume.pdf` remains the immutable Resume > Edit template only.

### Canonical scope and decision

- This story replaces the superseded Markdown-folder Story 8.5 in place. The canonical authority is `_bmad-output/specs/spec-experience-project-evidence-agent/SPEC.md` plus `documentation-contract.md`; their 2026-08-26 source-folder contract supersedes conflicting earlier Epic/UX Markdown-import language.
- The application-native local LLM owns execution. The app passes bounded selected-folder material to registered skills and validates their structured result. Do not expose a Codex handoff or developer prompt. [Source: _bmad-output/specs/spec-experience-project-evidence-agent/agent-skill-contract.md]
- `Resume.pdf` is immutable and belongs only to Resume > Edit. Legacy `base_resumes` / `current_base_resume_*` history remains retained but is neither read nor mutated by this active collection.

### Documentation-skill contract

- Inputs are exactly one explicit absolute local source folder and one explicit empty output folder outside it. The source can be a full working tree; it is never expected to be Markdown-only. The skill writes exactly these top-level, proposed/unreviewed artifacts after all preflight/stability checks pass: `project-overview.md`, `resume-evidence.md`, and `resume-bullet-candidates.md`.
- Apply the source-folder boundary exactly: resolve paths without links/reparse points; reject inaccessible/non-directory/non-empty/equal/nested output; bound traversal; inspect only allowlisted strict-UTF-8 text; exclude dependencies, VCS, build, coverage, cache, generated, binary, opaque, and unsupported content; snapshot before/after; never network, call a cloud/model, access the app DB, watch, retry automatically, use credentials, or mutate source. No output is published on failure.
- Use the existing templates as the schema: `resume-evidence.md` carries `### E-###`, atomic `Fact`, provenance, explicit unknowns, and `Proposed / unreviewed`; `resume-bullet-candidates.md` links `### B-###` to E-IDs. Code blocks never become factual prose. Preserve exact source-relative, slash-formatted provenance with nearest heading or `document` and one-based line.

### Application architecture and integrity

- The old code is Markdown-library infrastructure, not a safe source-folder importer: `src/files/evidence-library.ts` copies raw Project Markdown; `src/domain/evidence/evidence-library.ts` creates evidence from generic Markdown lines; `src/app/evidence-library.tsx` exposes the generic add forms; `src/app/evidence-library-workspace.tsx` combines it with Base Resume review. Refactor the active route away from those paths rather than weakening their safeguards.
- The native documenter reads only the bounded source snapshot and writes validated three-document output into managed `resume-evidence/<category>/<safe-name>/`. Its fixed-name artifact parser is deliberately separate from `candidates()` so a source line, overview prose, or bullet candidate cannot silently become evidence. Never persist raw source bytes or absolute source paths in the app.
- Evidence is proposed/unreviewed on import. Approval remains individual and immutable through existing evidence commands/revisions; only approved evidence may enter Coach selection. Audit entries remain metadata-only and must not capture raw contents or absolute paths.
- Keep filesystem/database operations server-side. Use a Server Component for the collection read model and a small Client Component only for interactive tabs/disclosure. Treat every Server Action field as hostile, validate at the boundary, return serializable safe errors, and revalidate only after successful import/review mutation. [Source: node_modules/next/dist/docs/01-app/01-getting-started/05-server-and-client-components.md; node_modules/next/dist/docs/01-app/02-guides/server-actions.md]

### UX and accessibility details

- Outer Resume mini-tabs must match `src/app/resume-workspace.tsx`; inner tabs show one selected category. Empty state makes the category-specific documentation action primary. The handoff text must make clear this is a real folder, source stays read-only, three proposed docs are created outside it, and later import plus each-item approval are required.
- A row displays friendly name, one overview-only summary, `3 proposed review documents`, evidence count/state, and **View details**. Details may name the three artifacts and expose existing per-item review actions, but never source path, ID, digest, prompts, model data, raw errors, or diagnostics. Keep focus on the disclosure control when toggled and use polite atomic status feedback for actions.
- Summary parser contract: remove front matter/comments/headings/blanks/fences, normalize a leading list marker, first meaningful paragraph, one sentence/240 characters maximum, otherwise `No summary found yet.` No factual-line fallback, no AI, and no evidence effect.
